# SM-S9110 — S9110ZCS8FZI1

Galaxy S23 base model, China (`SM-S9110`, `dm1q`, Snapdragon 8 Gen 2 / SM8550)
on firmware `S9110ZCS8FZI1`
(`samsung/dm1qzcx/dm1q:16/BP4A.251205.006/S9110ZCS8FZI1`), kernel
`5.15.189-android13-8-3251900-abS9110ZCS8FZI1`.

Status: **payload built and statically verified against this firmware's own
kernel image; not yet executed on hardware.** Every offset was derived from the
device's own `boot.img` rather than from a neighbouring build, and the build is
reproducible byte for byte. The KernelSU handoff is audited but untested.

## What this profile is

- The same engine as the other S23 targets: tracefs KASLR discovery with a
  physical P0 oracle fallback, controlled 32-object `mm_struct` collection,
  shaped order-3 SKB reclaim, the MCAST waiter writer, fake ashmem `fops`,
  configfs arbitrary read/write, pipe physical read/write, and a root usermode
  helper.
- This image shares its `.text` — and therefore every entry point the exploit
  needs (`ashmem_*`, `configfs_*`, `generic_file_splice_read`, `noop_llseek`,
  `init_task`, `system_unbound_wq`, `commit_creds`, `prepare_kernel_cred`,
  `override_creds`, `selinux_state`, `root_task_group`,
  `call_usermodehelper_exec_work`) — with `dm2q-S916BXXSAFZG1` and
  `dm3q-S918BXXSAFZF5`. Only the data segment moves:

| Macro | `dm2q-S916BXXSAFZG1` | `dm1q-S9110ZCS8FZI1` |
| --- | --- | --- |
| `KMALLOC_CACHES_OFF` | `0x020645f8` | `0x020647b8` |
| `ANON_PIPE_BUF_OPS_OFF` | `0x01e7f5e0` | `0x01e7f7a0` |
| `ASHMEM_FOPS_OFF` | `0x0200d638` | `0x0200d7f8` |
| `SLIDE_NFULNL_LOGGER_NAME_OFF` | `0x01d5de62` | `0x01d5de6d` |

  The three data pointers are `0x1C0` *higher* than the `dm2q` build, so the
  shift is not even the same sign as the sibling China S23 profiles; no
  neighbouring S23 payload can be reused here.
- The P0 oracle geometry is local to this build — `P0_ORACLE_PROBE_OFFSET
  0x1f0000`, 32 candidates in `0x10000` steps, `SLIDE_MAX_ATTEMPTS 32` — and
  `p0_fingerprint.h` is generated from this image, so fingerprints and
  candidates come from the same build.
- `SLIDE_TRACEFS_EVENT_ID` is `108` (`__TRACE_LAST_TYPE 20` plus a zero-based
  event index of `88`), and the two blocking `schedule` return offsets are
  `worker_thread` `0x0010db44` and `wait_for_vfork_done` `0x000c8fe4`.
- `target.h` requires the build to choose the stack writer
  (`#error FZI1 stack writer must be set by the build`); this profile is built
  with `-DSLIDE_STACK_WRITER=1`, i.e. MCAST.
- `P0_KERNEL_PHYS_LOAD 0x80080000` and `P0_PHYS_OFFSET 0x80000000` are taken
  from the other SM8550 profiles: this firmware ships a Qualcomm `abl.elf`
  instead of an Exynos `sboot.bin`, so the load address cannot be read back
  from the bootloader.

## How the offsets were checked

Three independent checks were run against the recovered image before the
values were written into `target.h`:

| Check | Covers | Result |
| --- | --- | --- |
| Symbol table comparison (`llvm-nm`) | 21 symbol-backed macros, including the four data-segment values, `init_task`, `selinux_state`, `root_task_group`, `system_unbound_wq` and the whole `ashmem_*` family | all match |
| Literal read through the recovered ELF's `PT_LOAD` map | `SLIDE_NFULNL_LOGGER_NAME_OFF` reads `nfnetlink_log` | matches |
| Pointer dereference | `SLIDE_NFULNL_LOGGER_OBJECT_OFF` (`0x02a91e48`) points at that literal; `SLIDE_RANDOM_TABLE_BOOT_ID_DATA_PTR_OFF` (`0x02bba9c8`) has `procname -> "boot_id"` and stores `SLIDE_SYSCTL_BOOTID_OFF` (`0x02e6c0b1`), which lands in the zero-filled tail of a `PT_LOAD` (`.bss`) | matches |

`ASHMEM_MISC_FOPS_OFF` is not a symbol: the recovered `ashmem_misc` is at
`0x02bfcf68` and BTF gives `offsetof(struct miscdevice, fops) == 0x10`, giving
`0x02bfcf78`. The raw `Image` layout has alignment holes and `.bss` has no file
bytes at all, so `virtual - _text` is not a valid file offset everywhere; the
checks translate through `vmlinux.elf` instead.

The payload itself is then re-checked: its identity string is present, all
`256` qwords of the generated fingerprint table appear in its
`.rodata`/`.data`, and it is confirmed to be a bionic shared library (no
`PT_INTERP`, no `ld-linux-aarch64.so.1` in `DT_NEEDED`).

`P0_PHYS_OFFSET` and `P0_KERNEL_PHYS_LOAD` are declared through `#ifndef`
guards, as in the sibling targets, so they can still be overridden per build.

## Why the existing S23 payloads cannot be reused

1. The four data offsets above are `0x1C0` higher than the `dm2q`/`dm3q` builds.
   A wrong data offset is invisible in the payload file and fails only at the
   KASLR/P0 stage on the phone.
2. A glibc-linked ELF cannot be used here at all. One install attempt failed
   with `CANNOT LINK EXECUTABLE "/system/bin/sh": library
   "ld-linux-aarch64.so.1" not found`, which is a payload built for a glibc
   userspace instead of bionic. The loader contract is now checked at build
   time, so this cannot reach the device unnoticed again.

## KernelSU handoff

The profile publishes `kernelsu/ksud-dm3q-S918BXXSAFZF5-kdp`, the
`android13-5.15.189` no-patch-text late-load build whose embedded module is
byte-identical to the `dm2q-S916BXXSAFZG1` module.

```text
undefined imports:                    200
missing from this device's kallsyms:  0
module __versions size:               0
vermagic (module):  5.15.189-android13-8-33413713-abS916BXXSAFZG1 SMP preempt mod_unload modversions aarch64
vermagic (device):  5.15.189-android13-8-3251900-abS9110ZCS8FZI1 SMP preempt mod_unload modversions aarch64
```

`CONFIG_MODULE_FORCE_LOAD` is unset on this kernel, but with
`CONFIG_MODVERSIONS=y` the kernel only compares the part of `vermagic` after the
first space, and that part is byte-identical, so the release-string difference
is not a load blocker.

Module initialization has not been tested on this device. The module contains
Samsung KDP/RKP/DEFEX handling and has an empty `__versions` section for
`ksud`'s kallsyms-aware loader, but its live hook setup can still reboot the
phone; treat it as a separate one-shot experiment after root is confirmed. The
only other candidate is `ksud-gts9-X710XXS6EZF1-kdp` (`4783256` bytes), whose
module is device-proven on the Galaxy Tab S9 and also audits clean against this
kernel.

## How to run

Through the app (Shizuku execution mode) or from an `adb shell` with the root
helper. The payload is a bionic shared library, so the app loads it with
`LD_PRELOAD` into `/system/bin/sh` or `dlopen`s it from the helper.

Expected signs of progress: `exploit completed` and `done=1 root=1`; when the
P0 oracle hits, `p0 fingerprint … best=8` with the matched row being the KASLR
offset. The KernelSU stage reports `KernelSU control verified`, or fails with
the `ksud` output attached instead of stalling.

Run soon after boot. Failures before the stack-writer stage are retried by the
supervisor; after it, the engine refuses in-boot retries (`stack writer ran;
refusing retry on this boot`), so reboot before trying again. If the
`p0 fingerprint … best=` score stays well below 8, the physical probe offset is
the first thing to revisit, and `P0_ORACLE_PROBE_OFFSET`, the candidate list and
the fingerprint table must be regenerated together.
