# Galaxy S23+ SM-S9160 (CHC) / S9160ZCS8FZI1 port

## Status

Device-tested on real `SM-S9160` hardware on 2026-10-31. The full chain ran from
`adb shell` (uid 2000, `u:r:shell:s0`) and returned uid 0:

```text
uid=0(root) gid=0(root) groups=0(root) context=u:r:kernel:s0
root
Permissive
5.15.189-android13-8-3251900-abS9160ZCS8FZI1
```

Proven chain:

```text
adb shell
-> tracefs KASLR slide (event 108, worker/vfork caller)
-> controlled mm_struct slab + shaped SKB reclaim
-> MCAST stale-waiter write (errno 99, sched_ok=1)
-> fake ashmem fops + configfs arbitrary read/write
-> pipe physical read/write (read_ok=1 write_ok=1 rw64=1/1)
-> workqueue usermode helper -> uid 0
```

KernelSU reuses the published S916B `ksud`, which loads on this device; see
[KernelSU](#kernelsu-existing-s916b-loader-hardware-tested). The profile is
registered in `support/targets-v3.json` and Root My Galaxy installed it
end-to-end in Shizuku mode on 2026-11-02; standalone mode is not supported, see
[App integration status](#app-integration-status).

The verified app run took two attempts: attempt 1/24 was killed by the app's
120 s budget during the controlled-mm group search, and attempt 2/24 completed
with `slide=0x28000`, 51 s preparation and `uid=2000->0`. The app then reported
`KernelSU control verified` and `install complete`.

## Firmware extraction

AP archive `AP_S9160ZCS8FZI1_..._meta_OS16.tar.md5` (15.9 GB) contains
`boot.img.lz4` (29,761,144), `init_boot.img.lz4`, `vendor_boot.img.lz4`,
`dtbo.img.lz4`, `super.img.lz4` and `meta-data/fota.zip`.

```text

             sha256 7253793787CA46BBA70C54AE0AB97CA2DF08A924653D4DF4FF7632A9684C7C1E
header       v4, header_size 1584, page 4096, ramdisk_size 0, signature 0

             sha256 8464C1B30A2887E824FB3954EA0832756F54990F1DDA03FA65484075C2C05852
ARM64        text_offset 0x0, image_size 0x2f50000, flags 0xa
```

`meta-data/fota.zip` → `BOOT/kernel` has the same SHA-256, which cross-checks the
extraction. The ramdisk is in `init_boot.img` (GKI layout).

`BL_...tar.md5` is a Qualcomm bootloader set (no `sboot.bin`): `abl.elf` is an
EFI firmware volume holding `Odin`, `LinuxLoader`, `Cryptest`, `QuestSOD` and
`QuestUSB`. `LinuxLoader` (ARM64 PE32+) performs the kernel handoff and logs
`Kernel Load Address: 0x%x`; the load base is RAM base + `0x00080000` +
`text_offset`, not an immediate in the image.

## Physical load addresses (P0)

```c
#define P0_PHYS_OFFSET      0x80000000ULL
#define P0_KERNEL_PHYS_LOAD 0x80080000ULL
```

`P0_PHYS_OFFSET` is fixed by the device DTB: `/proc/device-tree/reserved-memory`
exposes `gunyah_hyp_region@80000000`-family nodes (`cpusys_vm_region@80a00000`,
`aop_cmd_db_region@81c60000`, ...), so the lowest DDR base is `0x80000000`.
`P0_KERNEL_PHYS_LOAD` follows the Qualcomm ABL rule
`RAM base + 0x00080000 + text_offset(0)`, identical to the other kalama
profiles (`dm2q` S916B, `dm3q` S918B, `e3q` S928U1, X710). The target's own
P0 fingerprint check validated it on hardware:

```text
p0 physical write status=0 ok=1
```

## KASLR slide

`tracefs` event `sched:sched_blocked_reason` is ID **108** on this build, read
directly from `/sys/kernel/tracing/events/sched/sched_blocked_reason/id`.

Return-address offsets inside the linked image:

| Use | Offset | Anchor |
| --- | ---: | --- |
| worker | `0x0010db44` | `worker_thread` `bl schedule` at `0x0010db40` |
| vfork | `0x000c8fe4` | `wait_for_vfork_done` `bl schedule_timeout` at `0x000c8fe0` |

Observed slides across boots: `0x0000000000118000` and `0x0000000000128000`.
Both are 32 KiB aligned, so this firmware's KASLR granularity is 32 KiB, not the
64 KiB assumed by `src/slide.c` (`candidate & 0xffff`). The app payload
(`src/slide_app.c`, mask `0x7fff`) is therefore the only working slide path; the
standalone preload route reports `slide tracefs worker caller not found`.

Independent check: a raw `per_cpu/*/trace_pipe_raw` capture contained 392 copies
of `0xffffffc008235b44`, i.e. `0xffffffc00810db44 + 0x128000`.

## KernelSU (existing S916B loader, hardware-tested)

This profile does not need a new KernelSU artifact. The published
`kernelsu/ksud-dm2q-S916BXXSAFZG1-kdp` loads its embedded
`android13-5.15_kernelsu.ko` on this build. Reproduced on hardware on 2026-11-02
with the app's layout and argv:

```text
/data/local/tmp/ksud-s25u-kdp  = ksud-dm2q-S916BXXSAFZG1-kdp
/data/local/tmp/.ksud-stage   = the same binary (ksud renames it to /data/adb/ksud)
exec                          logcat late-load --package-name me.weishu.kernelsu
result                        /proc/modules: kernelsu 208896 0 - Live (OE)
```

The S916B `vermagic` is accepted because that module carries a `__versions`
section (zero length, no CRC entries). `check_modinfo` then takes the
`same_magic(..., has_crcs = true)` path, which drops the first space-separated
token from both strings and compares only
`" SMP preempt mod_unload modversions aarch64"`; the
`5.15.189-android13-8-33413713-abS916BXXSAFZG1` release token is not compared.
This kernel's `check_modinfo` (`0xffffffc00822a67c`) and the two comparison
strings (`0xffffffc009e6af18` full, `0xffffffc009e6af44` from the first space)
match that path.

Notes:

- the release token stops being ignored if the embedded module loses its
  `__versions` section, so a ksud rebuild must keep the module pair together;
- an earlier local experiment rewrote `vermagic` and loaded the module with
  `ksud insmod`; that was stricter than the app path and the rewritten module is
  not shipped;
- `ksud late-load` renames `/data/local/tmp/.ksud-stage` to `/data/adb/ksud`, so
  both staged copies must exist. Root My Galaxy stages both; a first install on
  a device without an existing `/data/adb` was not tested;
- the helper argv must stay `late-load --package-name ...`. This ksud's clap
  rejects `--ephemeral`; `src/su_daemon.c` currently adds it, so rebuilding the
  app helper from this tree would break this loader.

`ksud` scans `/data/adb/modules` while the LKM initialises, so stale or
incompatible module trees can make the load fail or hang. Root My Galaxy's
"Disable conflicting KSU Modules before KernelSU load" option (off by default)
moves the directory aside first; the equivalent manual step is:

```sh
adb shell '/data/local/tmp/rmg-s9160-root -c \
  "mv /data/adb/modules /data/adb/modules_bak && chmod 755 /data/adb/modules_bak"'
```

`su -c 'mv /data/adb/modules_bak /data/adb/modules'` restores it after the next
reboot.

Static audit of that module against this target's `vmlinux.elf`:

```text
undefined imports: 200
names present in target: 200
__versions size: 0        (no CRC gate, and the release-agnostic compare)
```

Hardware evidence: the 2026-10-31 run exercised the full KernelSU path with the
rewritten module (`su` -> `u:r:ksu:s0`, `ksud post-fs-data` ran a test module);
the 2026-11-02 run loaded the unmodified embedded module through the app's
`late-load` argv (`kernelsu ... Live (OE)`), and the Root My Galaxy install in
Shizuku mode completed the same day with `KernelSU control verified`.

## App integration status

Verified end-to-end on 2026-11-02 through the Root My Galaxy custom-source build
(PR #656) pointed at this branch: the app's Shizuku mode completed the exploit
and the KernelSU late-load and reported the install as successful.

- **Shizuku is required.** Standalone mode runs the helper as the app UID
  (`untrusted_app`); tracefs is denied, the payload logs
  `slide tracefs failed; falling back to physical P0`, and the physical-P0
  fallback does not root this build. This matches the shell-only status of the
  S916B sibling.
- The app's budget is unchanged (`P0_ATTEMPT_TIMEOUT_SEC=45`,
  `EXPLOIT_ATTEMPT_TIMEOUT_SEC=120`, `EXPLOIT_ATTEMPTS=24`, 90 s stall check,
  15 min total). The verified run confirms it is marginal: attempt 1/24 was
  killed at `timeout ... seconds=120` during the controlled-mm group search,
  while attempt 2/24 prepared in 51,234 ms and finished the chain.

## Follow-ups

- Keep Shizuku mode as the supported path; re-check slow boots if a later app
  build raises the per-profile attempt budget.
- Drop the `--ephemeral` argument from `src/su_daemon.c` (or make it
  KMI-dependent): the v3.2.5 loaders used by S916B/S918B/S9160 reject it.
- `src/slide.c`'s 64 KiB candidate mask should be relaxed to `0x7fff` if the
  non-app preload route is ever needed on this firmware.
