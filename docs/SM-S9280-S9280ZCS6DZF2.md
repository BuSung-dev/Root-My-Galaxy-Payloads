# SM-S9280 / S9280ZCS6DZF2 porting record

Port of the Galaxy S24 Ultra China (CHC) firmware support to the
Root-My-Galaxy-Payloads project. This is the first China-variant E3Q
(SM-S9280) profile in the repository.

## Offsets

The CHC DZF2 kernel shares the S24 Ultra E3Q layout but differs from the
international (S928B) and US (S928U1) DZF2 builds in two audited locations:

| Symbol | CHC (this profile) | International S928B |
| --- | ---: | ---: |
| `KMALLOC_CACHES_OFF` | `0x0176cbb8` | `0x0176c6f8` |
| `SLIDE_NFULNL_LOGGER_OFF` | `0x016a61b8` | `0x016a622a` |

All other audited offsets (init_task, root task group, selinux enforcing,
ashmem misc fops, sysctl bootid, loggers, `P0_ORACLE_PROBE_OFFSET`,
`ASHMEM_MISC_FOPS_OFF`) are identical to the S928B/S928U1 DZF2 profiles.

The P0 fingerprint table (`p0_fingerprint.h`) is generated from the exact
China raw kernel image and is **not** byte-identical to the international
table.

## Hardware validation

This payload was exercised on an SM-S9280 running the China DZF2 firmware
with the exploit triggered from the app domain (Shizuku mode). The same
`cve-2026-43499-app.so` binary shipped in this PR (`b233df62...`) is the one
used by the RootMyS24 project's DZF2 firmware entry, which was reported to
complete the chain (KASLR slide recovery → CFI fops slide → physical pipe
read/write → KernelSU late-load → granted `su`) on this hardware.

> Status wording: the maintainer should treat this as device-tested but with
> the caveat that the exact hardware run log lives with the contributor and is
> not yet attached as an artifact here. If a full run log is required, open an
> issue and it will be attached.

## Compatibility notes

- Firmware `S9280ZCS6DZG1` (a later build, same kernel version string) is
  **not** compatible with this profile; it needs its own `"nfnetlink_log"`
  offset and `kmalloc_caches` location.
- SM-S9260 / SM-S9210 (China S24+/S24) share the same kernel build string but
  have their own structure layouts; do not use this profile on them.
