## 4. Key hypothesis: kernel phys load

- FZF5 doc value `0x80080000` is an sboot-Exynos convention; sboot does not
  exist on Snapdragon, so it was rejected for this port.
- Working hypothesis: `P0_KERNEL_PHYS_LOAD = 0xa7e58000` (proven on S918B,
  corroborated by UEFI memory map entry `0xA8000000,0x10000000,"Kernel"`
  found by scanning the unpacked `uefi.elf`, entry `0xa7000000`).
- The APP build logs confirm the profile in use, e.g.:
  `phys_offset=0000000080000000 kernel_phys_load=00000000a7e58000 ...`.

## 10. mcast stack-writer route is INERT on this kernel (09-29, verified)

**Supersedes the "World A = route miss" phrasing in earlier notes.** Three
subagents reviewed this round; their conclusions conflicted, so every claim
below was re-verified directly against `/mnt/240G_SSD/s9180-fzg1/vmlinux.elf`
with an independent capstone harness (`/tmp/opencode/verify{1,2,3}.py`). Where
the subagents were wrong is recorded too.

### 10.1 The copy really is 0x108 bytes (subagent #1 was wrong)

Subagent #1 claimed `do_ipv6_setsockopt` copies at most
`sizeof(struct ipv6_mreq_src)` = 48 bytes, from mainline source memory. That is
wrong for this Samsung tree. Verified at instruction level:

```
+0x130  add  x0, sp, #0x40
+0x134  mov  w1, wzr
+0x138  mov  w2, #0x108
+0x13c  bl   memset                  ; zero sp+0x40 .. sp+0x147
+0x14c  cmp  w22, #0x108             ; optlen >= 0x108 ?
+0x150  b.lo fail
+0x154  add  x0, sp, #0x40
+0x158  mov  x1, x21                 ; optval
+0x15c  mov  w2, #0x108
+0x164  bl   copy_from_user          ; 0x108 bytes -> sp+0x40
```

Frame: `stp x29,x30,[sp,#-0x60]!` + `sub sp,sp,#0x260` = 0x2c0 total.
Optname 46 (`IPV6_JOIN_SOURCE_GROUP`) reaches that case: the jump table at
`0xffffffc009e4e1cc` has index 45 (optname-1) → `+0x12c`, confirmed by reading
the table entry. The socket-family check at `+0xfc` passes for our AF_INET6 fd.

### 10.2 The waiter slot is never read; the stamp header IS (corrected 09-29)

CORRECTION: the first version of this section claimed "no load ever reads the
copy range". That is **wrong**, and a review subagent caught it with exact
addresses. The error was in `tools/kernel_stack_slots.py`: a linear scan that
applies the epilogue's `add sp,sp,#0x260` to code *after* the `ret` at `+0x0be4`.
That later code is alternate switch-case bodies reached via jumps with `sp`
still at `entry-0x2c0`, so the tool misattributed their `[sp,#imm]` accesses.
The tool is fixed separately; the corrected facts, verified directly:

- copy destination = `entry_sp - 0x280`, copy range = `[-0x280, -0x178)`
  (from the `sub sp,sp,#0x260` at `+0x0020`).
- saved x29/x30 = `entry_sp - 0x60 / -0x58`; saved x28..x19 cover
  `[-0x60, 0x00)`. The copy range is disjoint from all of them.
- On the optname-46 path, reached by `+0x016c b -> +0x0ce8` **after** the copy
  succeeds, these loads execute with `sp = entry-0x2c0` and DO read the stamp:
  - `+0x0ce8 ldrh w8,[sp,#0x48]` → `entry-0x278` = stamp `+0x08`
  - `+0x0cf8 ldrh w8,[sp,#0xc8]` → `entry-0x1f8` = stamp `+0x88`
  - `+0x0edc add x8,sp,#0x40` / `+0x0ee0 ldr w1,[sp,#0x40]` → `entry-0x280` =
    stamp `+0x00` (reached via `+0x0d10 b.eq` on optname `0x2e`)
  - further `ldr w1/w8,[sp,#0x50]` (= stamp `+0x10`) and
    `ldp x9,x10,[sp,#0x40]` on sibling switch paths.
- The two `ldrh` compare against `#0xa` (`AF_INET6`) and branch to fail. So the
  stamp header steers the early-fail checks; attacker bytes are genuinely read.
- What REMAINS true: stamp `+0x78` (`entry-0x208`) is never loaded anywhere —
  the only reference is the store `+0x0c44 stp x9,x12,[sp,#0xb8]` on a path we
  do not take. The fake waiter is inert.
- What REMAINS true: the epilogue (`+0x0bc4 add sp,sp,#0x260`, then
  `ldp x20,x19,[sp,#0x50]` → `entry-0x10`, `ldp x22,x21,[sp,#0x40]` →
  `entry-0x20`) restores the kernel's own saved slots. No saved-register or
  return-address corruption; `autiasp`/`ret` intact. There is no register
  primitive.
- Tool fix: `tools/kernel_stack_slots.py` now does basic-block CFG sp
  propagation instead of a linear scan, and marks CFG-unreachable blocks
  (switch cases after `br`) as `unknown-sp` unless `--assume-sp` is given,
  in which case results are tagged `[ASSUMED]`. Reproduce with:
  `VMLINUX=/mnt/240G_SSD/s9180-fzg1/vmlinux.elf python3
  tools/kernel_stack_slots.py do_ipv6_setsockopt 0x00 0x108
  --assume-sp=-0x2c0` (the assumption is justified by manual trace of the
  incoming jumps `+0x016c->+0x0ce8` and `+0x0d10->+0x0dbe4`, both
  originating with `sp=entry-0x2c0`).

### 10.3 `MCAST_WAITER_OFF 0x78` is irrelevant, and stable-but-meaningless

`stamp+0x78` → `entry_sp - 0x208`: inside the copy range, never read. So the
offset is *stable* across devices but *inert*. Reviewer #3 put this well:
"0x78 is stable, and irrelevant; those are different claims and the profile
conflates them."

The S918B profile comment that "derives" it —
`0x10(sys)+0x70(__sys)+0x10(sock_common)+0x40(ipv6 bl do_ipv6)+0x2c0(do_ipv6 frame)`,
`greqs at sp+0x40; waiter E-0x2d8` — is **circular**. The copy destination is
inside `do_ipv6_setsockopt`'s *own* frame, so caller-frame arithmetic cannot
matter; and substituting the comment's own chain reproduces 0x78 as a tautology
rather than identifying a waiter slot. `sock_setsockopt` is also `sub sp,sp,#0x1a0`,
not the `0x10` the comment calls "sock_common".

### 10.4 The route oracle, correctly read (corrected 09-29)

All 58 runs log `ret=-1 errno=99 calls=1 sched_ok=1`. The first version of this
section called it a "negative oracle that proves nothing". That went too far:

- `errno=99` (EADDRNOTAVAIL) is produced at `+0x0cec mov w23,#-0x63` after the
  `+0x0ce8 ldrh w8,[sp,#0x48]` (stamp `+0x08`) fails the `cmp w8,#0xa` check.
  Since our stamp writes `AF_UNSPEC` (0) there, **the -99 is directly caused by
  reading our copied bytes**. So `ret=-1/errno=99` IS positive evidence that
  the 0x108-byte copy landed on the kernel stack and was read. It confirms
  route reachability through the copy and the family check.
- What it does NOT prove: waiter consumption. The waiter at stamp `+0x78` is
  never loaded (§10.2), and no `rt_mutex`/PI/futex code executes on this path.
- `sched_ok=1` is still literally `sched_setattr_tid(...) == 0`. It would print
  1 with the entire mcast stage deleted. No causality is asserted.
- `slide_consume_go` is still raised only **after** `setsockopt` returns
  (`slide_app.c:1309-1312`), unlike the pselect path which arms `go` *before*
  blocking. The frame is already popped, and it is a different task's stack.
- `calls=1` is still structural: the consumer sets `slide_consume_stop` and
  returns after one success (`slide_app.c:1876-1880`), so the
  `(calls % 19) + 1` policy sweep is dead code and only `SCHED_FIFO` is ever
  tried. `main.c:148-152` has the intended `CONSUMER_MAX_CALLS` loop that the
  mcast path does not use.

**Corrected reading: the oracle proves the stamp reaches the kernel stack and
is read; it is not evidence that the fake waiter is consumed.**

### 10.5 mcast cannot be the FZG1/FZF5 differentiator

Compared FZG1 against FZF5 (the device that roots). In `do_ipv6_setsockopt` the
prologue+copy region differs in exactly **2 instructions** out of 92 — the
`adrp/add` of the switch-table base, i.e. a relocation. **Zero branch-operand
differences.** The family-check tail and the epilogue are byte-identical. The
`memset`/`copy_from_user` sequence is byte-identical.

Since S918B (FZF5) roots end-to-end through the same mcast code, and the waiter
slot is unread on both, the mcast waiter **cannot** be what makes one device
root and the other not. Any root on S918B must come from the separate P0 / pipe
/ configfs physical primitive. (Narrowed 09-29: the stamp *header* is read on
both — see §10.2 — so "inert" applies to the waiter slot, not to every stamp
byte.)

Note: the S918B profile's comment "(FZG1 ships these +0x80)" is wrong; the real
delta on `KMALLOC_CACHES_OFF` / `ANON_PIPE_BUF_OPS_OFF` / `ASHMEM_FOPS_OFF` is
**+0x240**.

### 10.6 Two other suspected constants are dead code (confirmed)

`SLIDE_PSELECT_WORD_SHIFT 4` (FZG1; `3` is the value in the sibling
`dm3q-S9180ZHS8FZF5` profile, not in S918B which defines no shift) is a red
herring. The fallback `#define` (`slide_app.c:15-17`),
`slide_pselect_global_word()` (`slide_app.c:875-881`), and
`slide_pselect_stack_copy()` are all inside `#if !defined(SLIDE_STACK_WRITER)`
regions, and FZG1 builds with `-DSLIDE_STACK_WRITER=1`. (Precision: the FZG1
profile's own `#define`s are unconditional — only the fallback and the uses are
guarded — but the effect is the same.) Confirmed dead with `cpp`.
`SLIDE_PSELECT_TIMEOUT_NSEC` is dead for the same reason (its use is inside
`slide_pselect_stack_copy`).

Also verified: **all `FAKE_WAITER_*` and `FAKE_TASK_*` offsets are byte-identical
between the S918B and FZG1 profiles**, and the FZG1 values match FZG1 BTF exactly
(`USAGE 0x38`, `PRIO 0x7c`, `NORMAL_PRIO 0x84`, `PI_LOCK 0x884`,
`PI_WAITERS 0x898`, `PI_TOP_TASK 0x8a8`, `PI_BLOCKED_ON 0x8b0`). An earlier note
in this campaign claiming a 0xA0 difference was wrong. The comment at
`target.h:218-219` is correct.

### 10.7 Open lead: the postwrite readback is returning 0 bytes

Not yet investigated, but it blocks everything downstream. `cfi misc_fops
mismatch ... read=0000000000000000` means `pread` returned **0 bytes**, which is
not the same as "the address is wrong". The correct baseline is a nonzero
pointer (`ASHMEM_FOPS_OFF` = `0xffffffc00a00d7f8` + slide; a subagent confirmed
`ASHMEM_MISC_FOPS_OFF` lands exactly on `ashmem_misc+0x10`, the `fops` field, and
that this is the only ashmem fops table in `.kernel`, matching 7/7 ashmem
symbols). Fix the reader first — a read that returns nothing cannot distinguish
"wrong address" from "broken reader", and conflating them already sent this
campaign down the wrong path once. `fops.c:367-380` already has a `control`
probe emitting `pos0_ret`/`pos0_errno`; extend it to the 8-byte `pread`.
